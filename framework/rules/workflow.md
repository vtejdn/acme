# Research Workflow

Follow explicit human instructions and applicable agent instructions.
Apply the [core principles and interpretation](../readme.md#core-principles-and-interpretation) to every action and to conflicts, omissions, ambiguity and discretionary choices in this workflow.
Selectable research defaults follow [preference precedence](preferences.md#scope-and-adoption) within its permitted scope; repository settings and document choices do not by themselves waive evidence, preservation or authority boundaries.

## Agent and tool responsibilities

The agent reads the actual materials and decides content, work/edition identity, necessary homes and inputs, review applicability and authorization.
Tools optionally execute explicitly chosen objects, field updates, files and mappings, and report bytes, paths, differences, request/response facts and structural constraints.
The agent reads free prose, identifies actual references and purposes, prepares final text and checks affected consumers.
Ordinary creation, reading, import, intake and publication do not discover targets or infer source limitations from whole-body Markdown, mathematical, code or comment syntax.
Use bounded responsible declarations for mechanical identity, input, decision and review checks, and explicit addresses for actual target operations.
Selected-file or publication success covers only its actual byte, declaration, view and write checks, without certifying reference completeness.
For an actual [same-author transfer](intake.md#personal-import), the main agent determines the two-pass selection and retained homes, obtaining a subagent's direct mathematical comparison for concrete duplicate candidates under the [content rule](records.md#same-author-transfer-and-duplicate-comparison).
Tools do not infer family closure, cross-kind equivalence or review coverage, and this comparison duty creates no routine all-material review or new proof-certification claim.
At an actual public-reference operation, normalize and classify the final selected target before watching, reading its contents or checking an anchor, using the existing access rules and designated view.
For local navigation, use the existing single URL decoding and lexical components to reject protected targets and Windows trailing-dot/space aliases of source prefixes, including their necessary ancestors, before target resolution, reparse or existence checks.
Canonical logical source navigation supplies no source-file guard or availability condition, and ordinary preparation/publication does not resolve an unselected current or retired source root to classify another target.
Fixed Git intake and necessary acquired-record validation use the actual selected view throughout their consumers under the [intake rule](intake.md#scope-and-routing), without inspecting same-named sending worktree objects.
The agent chooses necessary inputs and canonical receiving arrangements; recorded local keys retain their owning repository/view, while actual local sources, Preparation and Batch publication keep their physical protections.
Apply the actual navigation, declared mathematical-input, concrete source-file or selected private-owner contract; a body link or native fragment alone supplies no stronger file-access or evidence obligation.
Keep a prohibited-target diagnostic, a missing necessary input and a stale selected fact distinct; do not expose private contents or automatically substitute another source, ancestor, input or decision to obtain success.
Tool success supplies no semantic equivalence, source adequacy, review sufficiency or permission.
For the actual operation, the agent chooses suitable available PDF reading, text extraction, page rendering, OCR and LaTeX compilation capabilities.
Reuse applicable host tools, project environments and build settings, confirming only what that operation needs without a compulsory inventory or fixed tool sequence.
Apply the [runtime rule](organization.md#machine-local-runtime) to continuing machine choices and relevant local notes, without requiring notes, activation or a new environment for an already adequate capability.
If a dedicated capability is absent, choose an adequate general tool or actually available alternative source format after checking the relevant version and applicability; another format establishes only the features it exposes, not PDF layout.
Supplement needed tools only within actual authorization and environment constraints, without automatic installation, configuration or bootstrap.
When a capability limit leaves required work incomplete, tell the human author in the normal response or handoff which source passage, formula, page, build or check is affected, how that limits the claimed result and what useful action remains.
Retain necessary substantive limits at their existing responsible home, continue unaffected authorized work and distinguish unperformed inspection or compilation from actual results.
Apply the existing [progressive-reading](literature.md#progressive-reading), [local-build](writing.md#reproducible-local-builds) and [temporary-storage](organization.md#temporary-storage) duties; document build workspaces are not an alternate home for disposable literature text extraction or literature page images.
Check the result and necessary direct consumers; record required facts in their existing homes without a confirmation flag, receipt or compulsory command.
For an explicit J source refresh, the agent identifies the same original and selected current scope and maintains necessary retained inputs and actual consumers under the [intake rule](intake.md#homes-and-independent-reuse).
Copying selected files supplies no consumer or mathematical review, and earlier acquisition scopes do not select themselves as current dependencies.
Useful source-edition explanations belong in concise author source notes, and actual inspected mathematics and checking limits belong in rolling U or adequate C/L.
No literature registry, holding ledger or fingerprint mechanism is maintained; ordinary shared reading and logical source navigation neither query local originals nor infer possession.
Actual personal import and external intake complete the agent-selected necessary original preparation and report true failures under the [literature rule](literature.md#acquisition-before-u-reception); same-repository reuse prepares originals only for necessary further reading.
Typed namespace occupancy, fixed identity entrances, numerical/field constraints, OS locking, exclusive creation, stale-input refusal and rollback remain mechanical responsibilities.
Direct collaboration, same-human body maintenance, shared navigation/registration and the two kinds of actual conflict follow the [identity rule](identity.md#collaboration-maintenance-and-conflicts).
Apply its scoped mathematical-recheck approval only when that conflict actually arises; ordinary authorized research and maintenance keep their existing authority.

### Prepared work and input applicability

Before publishing a prepared declaration, association or decision that relies on previously read content, confirm that its input still identifies the intended object and supports the prepared use within actual authority.
Reuse current-context reading and judgments while they remain applicable.
After a relevant change, Task switch, interleaved work or concrete uncertainty, reread only the affected content and judge the necessary adjustment.
Judge object continuity, mathematical applicability, review sufficiency and authorization from the actual materials and instructions, including when paths and anchors match or structural checks succeed.

Coordinate affected dependency-changing writes in the supported working copy, including Task release and reuse.
If a relevant modification could intervene between confirmation and publication, preserve the confirmed premise through existing write coordination, selected expected-content comparison or an equivalent guarded edit.
When choosing expected-content publication, supply the actual selected input used for preparation, including when its locator matches and address reuse is unknown.
Keep any necessary final comparison and publication within the same existing short write protection.
Keep mathematical reading and reasoning, network access and long computation outside that protection.
Select only the preparation inputs needed for the actual operation.

If a selected preparation input changes, hold the old prepared result while establishing what still applies and preparing any necessary adjustment.
Assess a byte difference for its actual mathematical effect before choosing the necessary revision, review or authorization step.
Retain sufficient prior work when its mathematics and intended use remain valid, preserving actual authorship, source facts, review scope and effective conditions.
Retain earlier evidence at the inputs actually inspected and confirm a finding's actual scope and adequacy before selecting it for completion.

Apply this responsibility to dependent Task append, revision and selection, formal R bindings, an individual Task's joint-parent declaration and an S material's explicit Task association.
Tools report their actual field, type, path and locator checks and compare only the expected content explicitly selected for comparison.
The agent reads free prose and judges its dependencies and mathematical applicability under the actual operation's scope.

Each S owns route priority/disposition and exact Task associations.
Fixed arguments, rolling source units and computation groups own their actual mathematics, while formal R findings own their actual agent review scope and relationship.
Indexes derive navigation rather than creating another status authority.
Link the actual responsible material and preserve necessary mathematical and evidentiary change history there.

The Claim index provides short per-Claim navigation.
Detailed dependencies, extraction provenance, necessary authority facts and proof-version transitions stay in the linked responsible records.
Administrative and authorization chronology follow the [common content decision](records.md#substantive-material-retention), without a separate historical-retention duty.
Task, strategy and ledger indexes organize their own objects; they must not accumulate duplicated cross-module progress reports or routine check logs.

Current research choices and reusable route lessons belong in strategies; arguments, source checks, counterexamples and reviews stay at their responsible mathematical homes.
A parent organizes branches without owning their proofs or granting a new Task authorization.

Keep [mathematics/readme.md](../../mathematics/readme.md) as a short stable entrance to Task, Claim and strategy navigation and the responsible materials.
Read current decisions and continuation points at those homes.
Do not maintain a synchronized cross-Task progress page or require an overview edit at Task completion.

Substantial mathematical comparisons may belong in a fixed thematic synthesis with real mathematical content and appropriately registered deductions.
Keep useful earlier assessments in their actual [historical accounts](ledger.md#exploration-and-history), and verification details with audits or computations.
Do not recreate a rolling cross-Task progress page under another filename, a dashboard or a summary registry.

Use the Claim index, responsible object records and stable mathematics entrance directly.
Remove obsolete navigation pages after updating incoming links and nearby ownership labels, including in reviewed documents.
Pure navigation and metadata changes do not create a new mathematical proof version; preserve their actual reviewed scope under the [artifact-maintenance rules](proof-audits.md#navigation-maintenance).

## Exploration, Registration, and Acceptance

Before direct creation/registration or retention of C/J/R/L/U, apply the [common content decision](records.md#substantive-material-retention) to necessary content and adequate existing homes, then the kind-specific obligations.
A draft is not a prerequisite, and an already adequate record needs no duplicate.
Apply obligations to the current action and intended use of each material.
Exploration, candidate registration and acceptance can occur together within one Task; they are not successive gates, a global Task mode, or new status fields.

| Action | Required scope and evidence |
| --- | --- |
| Explore a question or test a mechanism | Identify the current question, attempted range, provisional assumptions and what the next test could distinguish. The final statement, hypotheses or quantifiers may still be developing. An authorized experiment or conditional derivation does not require a Claim ID or a completed mathematical review before it can begin or continue. |
| Register a candidate or organize a substantive reusable project statement | State the proposition precisely, identify inputs/gaps and register under the [Claim rules](claims.md#claim-registration). A real unresolved assessment may select open; an unselected C creates no initial decision or date and registration certifies no result. |
| Accept a result as established, adopt a checked refutation or report Task completion | For proved/refuted assessments, check the complete supporting argument or refutation, applicability, resolved mathematical dependencies and applicable [review evidence](proof-audits.md) under the [assessment rules](claims.md#separate-assessment-fields). For a Task, apply its stated completion criteria to its actual deliverable. Existing accepted inputs and compatible inherited reviews retain their recorded scope. |

The following events determine when additional obligations apply:

| Trigger | Required action |
| --- | --- |
| Substantial proof investment, including a nontrivial intermediate step | Perform [knowledge reuse](knowledge-reuse.md#reuse-before-proof) before that investment. Routine direct calculations do not require a search for every line. Calling sustained proof work exploratory does not remove this trigger. |
| Recognition of a named or established result | Apply the independent [source-check trigger](knowledge-reuse.md#recognized-known-results) during exploration, completing or explicitly retaining the outstanding check before handoff. |
| A finding becomes useful, affects the research direction or must support continuation | Preserve a sufficient [exploration record](ledger.md#exploration-and-history). Routine scratch work without a substantive finding needs no separate operation log. Retained or cited computation evidence follows the [computation rules](computations.md). |
| A substantive project statement is organized for reuse, or an identified conjecture/obligation needs a canonical record | Apply Claim registration, preserving actual dependencies and an assessment only when truly made; key Claims and the adopted completion chain require explicit applicable assessment under the [Claim rule](claims.md#mathematical-assessment-and-review-findings). Routine source specialization follows knowledge reuse. |
| A result is treated as established, selected as reviewed support or used to close a Task | Satisfy the applicable acceptance, proof-selection and completion requirements before updating the responsible assessment or reporting that outcome. |

Always distinguish verified inputs, provisional assumptions, computational observations and checked arguments.
An unresolved hypothesis may be used to explore its consequences, provided the premise and resulting conditional scope stay explicit; it cannot silently become an established input to an unconditional conclusion.
Local checks are useful at any point and do not require completion of a whole review before further exploration.

These rules operate within the authorized Task or current instruction.
Existing execution limits, source-intake requirements and protected [main-theorem/objective decisions](claims.md#lemma-extraction-and-approval) retain their own triggers.
Within an already authorized assignment, do not introduce an additional stage-transition approval, a mandatory Claim for every experiment, or an additional log or directory merely to apply this section.

Continue arguments directly in D and continued/reusable programs in their responsible J program home.
Generated output uses that J's `mathematics/computations/outputs/<J>/` home under the [computation rule](computations.md#computation-output-location).
A failed or unreviewed attempt is still mathematical work, not a reason to place it in root temporary storage.
Keep useful findings and failures at their responsible homes; a handoff links those materials.
Small interactive trials need no new record.
The [temporary-storage boundary](organization.md#temporary-storage) permits operational isolation without creating a scratch-to-accepted stage.

## Proportionate Execution

Select the activity covered by the current instruction before reading or changing records: discussion, maintenance, Task setup, research advancement, or review.
Apply the [core autonomy principle](../readme.md#core-principles-and-interpretation) to proactively complete necessary work, verification, integration and delivery within that activity's actual authority and effective limits.
An analysis-only assignment retains its analytical deliverable; authorized retained writing includes its applicable delivery without requiring another routine operation request.
Before starting or continuing affected work, read the current local [version metadata](../version.json) and entrances, then the current rules governing that activity, the relevant object and its directly needed inputs.
Reread the current needed entrances and governing rules before dependent operations when the installed framework version changes, an applicable rule's content, authority or scope changes, or the continued applicability of earlier actual reading cannot be established.
This includes an upgrade during an existing assignment and local rule edits before version advancement; an unchanged version number does not establish unchanged applicable text.
Old conversations, compressed summaries, persistent memory and recollection of an earlier framework version may locate relevant files but cannot replace the required current-file reading or establish that old instructions remain applicable.
Reuse only actual reading in the current context whose continued applicability is established; a remembered assertion that the rules were read is insufficient.

Reusing a daily public-version result, an unavailable result, disabled or offline network checks and delegation do not waive this current-rule duty.
Subagents read the current rules needed for their assigned activity even when reusing the responsible main agent's metadata result.
A newer official version that has not been installed does not replace the governing local rules or authorize treating remote instructions as current local authority.
After an authorized upgrade, apply the rereading duty before resuming affected work, preserving the assignment's actual authorization and Task/E stopped conditions.

Read only the assigned work's needed rules and direct inputs, without an unrelated full-framework or historical-library reread on every turn or tool call.
A new tool call alone is not a reason to reread the same rules or an unrelated historical example.
Use bounded searches/section reads.
If output is truncated, recover the missing applicable text and exceptions before acting; a partial output is not a completed read.
Do not add a last-read-version field, reading register, rule fingerprints, receipts, signatures or a script that certifies reading or understanding.
Current-file reading and judging the continued applicability of earlier actual reading remain agent responsibilities.

Keep each fact in its responsible record and update only necessary consumers.
Finish the affected edit/publication batch before maintaining its navigation and checking the final prepared bytes.
Do not check generated output while another command is still changing it.
Repeat a passed check when relevant bytes change, a failure is repaired, or a new risk justifies the additional scope; do not repeat it merely for another status update.
Working files, staged contents and committed trees are distinct; inspect the actual bytes needed for the requested operation under the [delivery rules](identity.md#submission-checks).

Normal success needs a concise result.
Expand diagnostic output for a failure, unexpected scope or a requested investigation.
Wait on an already running command instead of launching duplicates; use a suitable bounded waiting interval and provide meaningful progress when useful.
An unexplained delay calls for a targeted diagnosis, not repeated generation or a broad audit by default.

These are execution defaults, not a new reporting system.
Do not create per-read logs, permanent timing ledgers, validation receipts or another status registry to demonstrate compliance.
Keep substantive mathematical findings and actual review evidence in their existing homes.

## Repository work starts

For a Git-managed working repository with a configured remote, the responsible main agent obtains fresh facts about the applicable project branch before substantive work on a newly assigned repository task, a resumption after pause or interruption, or a new autonomous exploration round.
This applies to single-human projects, ordinary and joint research, writing, literature preparation, review, maintenance, framework development and upgrade preparation; multiple authors, a joint T or a collaboration-mode declaration are not prerequisites.
Here a task is the actual repository assignment, not necessarily a mathematical T; checking a remote creates no T, E or decision record.
First read the current local version and necessary entrances to establish the assignment, working branch and explicit limits, then use native Git to determine the applicable project target and protected local work.
For ordinary first installation, the [installation target check](../agent-actions.md#first-install-empty-target) precedes source preparation, writes and project integration; a known nonempty local target or project remote stops that installation instead of being merged first.
Proactively obtain fresh remote facts and needed commits, complete any necessary authorized fast-forward or ordinary merge without a separate routine instruction, and read affected current rules and inputs before starting substantive task work.

Continuous reading, tool calls, substeps and progress questions within the same assignment may reuse the round's actual result while it remains applicable.
The main agent coordinates integration and writes in that working copy; subagents reuse its result while reading their own applicable current rules.
A new task or resumption needs fresh project facts even if a query ran earlier that day; old remote-tracking references and the daily official framework-version cache do not supply them.
Refresh again when known relevant remote changes, a phase needing fresh facts or actual delivery requires it, without polling or a mandatory query for every call.

Use native Git under the [target, authority and integration rule](identity.md#shared-repository-updates-and-integration); one actual fetch can establish fresh facts and obtain the commits without a separate connection-probe sequence.
With no incoming update, continue without an empty commit or synchronization event.
After integration, read the changed rules, contracts, strategies, results, useful failures, reviews and source facts relevant to the current work before adopting or editing affected content.
Reread changed applicable rules under the [current-rule duty](#proportionate-execution).
A Git update creates no intake, adoption of a new exact joint contract, execution activation or resumption; it does not reset effective stops or renew an allowance.
Honor the [execution boundary](execution.md#responsibility-and-version-boundary), actual author scope and fixed inputs; explicit offline, read-only and fixed-commit instructions and failures use the integration rule's bounded handling.
Without Git or a configured remote, perform no project-remote update; do not install Git, initialize a repository or add a remote solely for this duty.
The official daily version check keeps its separate setting and scope.
If a Git-managed repository cannot currently use Git, report the actual capability limit instead of treating it as a non-Git folder.
No round number, last-sync field, synchronization log, model register, scheduled service or receipt is required.

### Integration capability and delegation

Before making integration judgments, the main agent assesses whether its actual model and reasoning configuration are adequate for the affected content.
If its model has lower reasoning capability or its current reasoning effort is low, it must bring in an actually available, stronger model suited to the integration, with appropriate reasoning effort, to perform the necessary judgments and result checking.
Apply this especially to mathematical statements, hypotheses, proofs, input dependencies, source editions and review applicability; a clean Git merge or a mechanical check cannot establish those conclusions.
Judge suitability from the actual task and platform capabilities, without a model-name classifier, file-extension rule, fixed ranking or automatic router.

Provide the delegate with the necessary current rules, explicit local and remote commits and differences, actual materials, authority, pending questions and affected consumers.
The main agent retains overall understanding and responsibility for scope, attribution, coordinated writes and checking the necessary result.
Delegation supplies neither additional author rights nor substantive-conflict review approval, and independence still follows the actual participation and [review boundary](proof-audits.md#review-arrangements).
An adequately capable main agent may act directly; merely obtaining or reading branch facts does not require another agent.
If adequate model, reasoning or delegation capability is unavailable, state the affected judgments and unfinished scope, defer dependent processing and continue independently supported authorized work.
Do not claim an unavailable model participated or create a capability certificate, compulsory call sequence or new approval procedure.

## Registering and Activating a Task

### From an inquiry to approved research

Determine the human's requested answer and actual instruction scope from its meaning, including a conversationally phrased research proposal.
Use relevant existing Task contracts, strategies, mathematical materials and source evidence, completing the applicable [work-start update](#shared-repository-work-starts) before substantive work.
Perform proportionate [preliminary lookup](literature-search.md#autonomous-literature-search) where the available evidence is insufficient.
An adequate short explanation, direct calculation or established result can answer the question without creating a Task or requesting formal-research approval.
The agent judges when the lookup supplies enough orientation; it requires neither external search nor a fixed number of queries or attempts.
Reuse adequate earlier lookup and stop a clearly unproductive branch at its actual scope.
Distinguish a mathematical gap from an ambiguous formulation, an access failure or an unchecked source; unsuccessful lookup proves neither novelty, nonexistence nor the absence of a known solution.

When an initial inquiry remains unanswered and further work requires formal strategy exploration and sustained Task advancement, report the situation and request human approval before that transition.
An initial request for an answer, framework installation or an unsuccessful lookup alone does not authorize it.
Give a concise account of what the preliminary work established, what remains unresolved and the concrete research scope proposed, including known decisive constraints or missing facts.
Make clear that approval would authorize the responding agent to reuse or establish the appropriate Task, take main research responsibility, explore strategies and advance that objective.
Use an ordinary response without a compulsory form, budget questionnaire or invented effort estimate.
Wait for an actual applicable human response before dependent formal work; silence, elapsed time, a tool result or confidence supplies no approval.
Honor refusal, deferral and narrower approval at their actual scope.
Before approval, remain within the initial assignment and its retention and literature duties; do not activate a research Task, start its E or conduct the proposed comprehensive strategy campaign as approval preparation.
Presenting the proposal requires no proposed Task, approval document or new research container.
An explicitly requested question registration may use the proposed-Task route below.

Reuse an existing explicit instruction or approval covering formal research on the same objective and scope, including a direct instruction to establish and pursue its Task.
An inconclusive lookup, continuation, new exploration round or new session creates no recurring approval requirement while that authority remains applicable.
Preserve all still-effective human restrictions, execution stops, shared limits and resumption conditions.
A new objective or expansion beyond the approved scope needs its actual applicable authority.

This boundary concerns the initial inquiry's transition to formal research, without a global research mode, search-failed status or sequential acceptance protocol.
Pure explanation, a bounded literature request, a source audit, maintenance and an explicitly limited plan retain their actual deliverable and scope.
An unanswered bounded request does not become an assignment to prove the underlying assertion.

After sufficient approval, apply the [Task rules](tasks.md#task-records), [main-agent and execution responsibilities](execution.md#main-agent-responsibility-and-exact-maintenance) and [strategy-selection rules](strategies.md#choosing-and-revising-a-route) without another routine grant for setup, main responsibility, ordinary methods or the next authorized investigation.
Keep necessary current authority and scope in the existing responsible Task decision or E conditions when they actually change.
An unchanged authorization needs no new decision, full approval transcript, timestamp history, receipt or parallel permission ledger.
Approval to explore strategies and advance the objective calls for substantive investigation under the [follow-up rule](#candidate-research-follow-up); Task/S/E preparation or a list of possibilities alone does not fulfill that assignment.
Continue within scope until the actual completion criteria are met, an effective stop applies or a decisive missing human fact or authority prevents dependent progress, retaining necessary findings and continuation points at their responsible homes.

### Task registration and activation

Apply the [Task rules](tasks.md) and distinguish registration, authorization, review and execution:

| Instruction or situation | Normal result |
| --- | --- |
| Record a question awaiting authorization | proposed Task |
| Establish a clearly assigned research objective | active Task under the actual assignment |
| Continue an existing objective | Inspect its current contract and lifecycle; use the existing Task when it is the intended objective |
| Begin research as well as establish the objective | Complete setup, then apply the execution policy and any recorded stop/resumption conditions |

Check the relevant Task index and likely matching contracts to avoid accidental duplication.
Write one precise contract with the target, hypotheses and quantifiers, scope/conventions, completion criteria, actual authorization, and necessary starting references.
A descriptive anchor can be fixed before allocation; when choosing the optional allocator or writer, use its actual returned ID instead of predicting the next serial.
Direct authoring follows the same [allocation state and concurrency protections](identity.md#allocation-and-concurrency).
Optional template sections need content that helps continuation, not placeholders proving that setup occurred.

Register a clear assignment with its complete contract, actual human author and initial decision with date, proposed/active status, real authority/reason and exact contract relation.
The optional writer `python scripts/material.py create --kind T --file task.md` allocates and returns a canonical path, defaulting an unspecified new Task to A under the [Task rule](tasks.md#task-records).
An active assignment needs no invented setup review, second activation decision or execution run.

Activation does not require a separate contract-review document.
Record a genuine review when performed, with its actual scope; retain its concrete findings without a Task-wide review label.
A new completion still requires its applicable completion review.
Task setup alone does not require a Claim, strategy, audit file, mathematical-operation entry, maintenance report or independent reviewer.
Add related records only when the substantive work calls for them.

Update necessary links and generated navigation when the new objective affects them, then check the final affected changes.
Task setup alone creates no E and grants no execution, usage baseline or allowance; prepare or reuse the local boundary only for actually selected execution under the [execution rule](execution.md).
A joint coordination T has no E and is used through the actual human's individual Task.
Keep live run state out of the contract and the mathematical Task decision; use a stable link to the [execution rules](execution.md).
If the instruction also authorizes immediate research, continue under those rules without another setup approval.
An active Task does not resume a stopped run or bypass an applicable execution limit.

## Starting and Continuing Work

Begin or resume with read-only inspection.
During discussion, reading and maintenance analysis, answer directly for explanations of existing material, routine short calculations or exploration with no lasting use.
Cite adequate existing materials when useful.
For an unanswered initial inquiry, apply the [reporting and approval boundary](#from-an-inquiry-to-approved-research); an approved research assignment then follows the advancement sequence below.
When that work produces mathematics worth retaining, apply the pre-delivery preservation duty within actual authority.
See [Closing an Exploration Round](#exploration-round-closeout).
Before research advancement inspect the relevant selected material decisions, contracts and execution state.
Within the current human, Task, route and material scope, read relevant `mathematics/maintenance.md`, `mathematics/erratum.md` and `mathematics/messages.md` when present under the [coordination rule](records.md#shared-mathematical-coordination).
Before actual mathematical reliance, inspect applicable local-material erratum and relevant source evidence for the chosen input and version, including other-author dependencies.
Reuse adequate reading while it remains applicable.
Route new source defects and local misreadings, misuse or failed dependencies by their [actual mathematical object](records.md#mathematical-issues-and-reliance), rather than putting every external-source problem into erratum.
Recipient handling and human-authorized sender archives follow the [message rule](records.md#mathematical-messages), without changing Task/E or automatically loading personal message archives.
Routine startup does not trigger a full audit.
Choose any useful scoped material, link or storage checks for the actual question, and resolve relevant findings before relying on them.
A stale index does not change the authored decision.

Refresh navigation after the affected material/configuration batch has settled, when its view is needed.
The responsible agent may edit affected C/T/S navigation directly from the responsible materials and exact selected decisions, including populated generated rows, or use `python scripts/render-research-navigation.py` when useful.
Coordinate the affected write scope before editing and preserve unrelated and concurrent changes; reuse adequate navigation until relevant inputs change.
The optional renderer derives the indexes without a catalog authority or full proof/history audit, retaining its short lock, input rechecks and shared publication protections when selected.
For bounded discovery, use ordinary scoped search and reading or the optional `material.py discover`, `indexes` or `routes` commands with their stated scope.
Use operation-local material and reference readers for the actual question; completed authoring or rendering adds no aggregate delivery audit.
Run observations and execution queries do not trigger mathematical navigation regeneration.

The following sequence applies to mathematical research advancement, including an approved transition from discussion; explanation, maintenance and Task setup alone retain their applicable scope above.

1. Read the root README and the stable mathematics entrance, then verify the relevant objective in the [task index](../../mathematics/tasks/index.md).
   Check the working tree before editing and preserve existing work.
   Maintenance and discussion alone do not select a new research step; use the actual approved assignment under the [inquiry-to-research rule](#from-an-inquiry-to-approved-research).
   Before autonomous task advancement, read the actual operator's applicable personal execution policy, the current Task contract and its stable [E record](execution.md), including still-effective stopped conditions.
   Obtain required fresh readings at the policy's boundaries without retaining a quota diary or temporary response.
   Keep only the current exact Task reference, state and still-effective conditions in the stable E, with an incremental baseline/window only when actually applicable.
   Stop on the first stopping observation or monitoring failure and directly retain the effective stopped condition.
   An active Task does not itself resume a stopped run.
   For a Git working repository with a configured remote, complete or reuse the [common work-start update](#shared-repository-work-starts) before substantive work and read its relevant changes before relying on the local entries below, including when existing mathematics makes a new external search unnecessary.
2. Follow the relevant [Claim entries](../../mathematics/claims/index.md) and [strategy index](../../mathematics/strategies/index.md) within the authorized task.
   Read the linked arguments and audit units needed for the next step; do not treat historical checkpoints as active instructions or reread unrelated history by default.
3. Identify the current question, known and provisional assumptions, and smallest useful next step under the [work-obligation rules](#work-obligations).
   During exploration, state which parts of the eventual target remain to be determined.
   Prefer resolving a known gap or testing a concrete mechanism over starting an unrelated line of inquiry.
   Use the [route-selection rules](strategies.md#choosing-and-revising-a-route) to judge the next step, including any inexpensive probe that could change a decision before substantial investment.
4. Before substantial proof work, apply [reuse before proof](knowledge-reuse.md#reuse-before-proof), including for intermediate steps.
   Read, derive, compute, or search for counterexamples as appropriate.
   Preserve substantive evidence in its responsible record, including unsuccessful approaches and their exact scope.
5. Update the responsible evidence and affected Claim entries; reconsider route priorities when appropriate and update task records/index when their authorized scope, selection or completion changes.
   Leave the relevant records sufficient for another agent to resume without relying on chat history.

When choosing routes or responding to an obstruction, apply the [route-reuse and applicability rules](strategies.md#choosing-and-revising-a-route) and cite fixed evidence for mathematical reliance.
Receive prepared local content under the common [adaptation rule](records.md#receiving-and-adapting-selected-content), retaining exact necessary source scope and the original human.

## Mathematical Standards

- When undertaking a proof of an identified proposition, state its hypotheses, quantifiers, notation and conclusion precisely.
  Exploration aimed at finding that proposition follows the [work-obligation rules](#work-obligations); it may start from a question and provisional scope.
  Separate the original question from any stronger or weaker candidate.
- Label an established reduction as necessary, sufficient, or equivalent, with justification.
  A proposed relationship may remain explicitly heuristic or conditional.
  A failed stronger sufficient condition does not refute the task; a proved reformulation alone does not resolve its remaining obligation.
- Make the mathematical setting explicit when relevant: the algebra or operator algebra, the state or trace and its properties, boundedness or operator domains, the notion of independence, and the topology or mode of convergence.
  Check normalization conventions before combining results from different sources.
- Verify applicability before using a result as an established input.
  During a conditional exploration, mark any unchecked premise or interface and carry that limitation through the conclusion.
  Record actual dependencies and enough detail to reconstruct each nontrivial inference; do not hide a missing argument behind phrases such as "clearly" or "by standard arguments."
- Distinguish algebraic identities, analytic arguments, asymptotic statements, and numerical evidence.
  Finite matrix experiments, truncated expansions, and agreement with examples do not establish a general theorem or a limit interchange.
- Actively test boundary cases, degenerate cases, and plausible counterexamples.
  Check whether the proposed conclusion survives the loss of each essential hypothesis.
- Never fabricate citations, theorem statements, calculations, proof checks, or novelty claims.
  Mark uncertainty explicitly.
  Failure to find a result in a bounded literature search does not establish that it is new.
