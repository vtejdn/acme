## <a id=setup></a>设置指令

这些示例用于准备工作区、登记作者身份和配置本地资源。
安装与登记的步骤顺序见手册的[设置](../用户手册.md#setup)。

| 指令示例 | Agent 的预期行动 |
| --- | --- |
| 把 ACME (https://github.com/vtejdn/acme) 下载并安装到目录 `D:\my-math-repository` | 核对指定目录的现有内容，将所选官方版本的框架文件整合到实际项目根目录，保留已有内容和 Git 历史，不带入官方仓库的 Git 元数据。复用已有项目与作者信息，补齐必要设置，核验根目录中的框架版本和入口，报告实际安装位置、版本及未完成事项。 |
| 安装 [Git](../git-repository.md#notion-git) | 确认是否已安装 Git；需要时安装，并报告可用版本和必要的后续设置。 |
| 将 Ali 登记为我的作者键，姓名使用 Alice。 | 核对作者键和已有登记，使用已提供的 `Ali` 作为作者键、`Alice` 作为 `LICENSE` 署名。登记你的身份，添加署名并保留已有身份和声明；若当前工作副本使用 Git，将其关联到 `Ali`。 |
| 告诉我如何连接 [GitHub](../git-repository.md#notion-github) | 说明登录、认证和连接远程仓库的步骤，并指出需要你完成的操作。 |
| 我已经登录 GitHub，进行连通测试 | 核对当前认证账号，以只读方式测试 GitHub 和目标仓库的可达性，并报告连接结果或具体错误。 |
| 设置仓库键为`仓库键` | 验证所选仓库键，记录有效值并更新受影响的当前引用；无效时请你另选。仓库键独立于项目缩写、全名和 README 标题，作者键、材料身份和历史来源事实按原有含义保留。 |
| 设置仓库缩写和全名为`仓库缩写`，`仓库全名` | 记录你分别选择的项目缩写与全名，确认均为非空单行文本；用两项形成 README 主标题“〈缩写〉: 〈全名〉”，使配置与标题一致并保留其余正文。仓库键与这两项分别设置。 |
| 设置 Git，连接到我的仓库 <https://github.com/alice/acme>。 | 仅在需要时初始化 Git，按你的选择补齐缺失的仓库名称或作者登记，并将工作副本关联到你的作者键。核对或配置提交身份，使其与登记对应，连接指定远端，并通过相关账号或认证通道测试访问。保留已有提交、不相关设置和 Task 限制，报告已配置的目标及剩余设置事项。 |
| [克隆](../用户手册.md#notion-clone)我的合作者仓库 <https://github.com/alice/acme>，并将我登记为 Bob | 克隆共享仓库，核对作者键 `Bob`、你的实际身份和已有登记；首次登记时先补问独立选择的 `LICENSE` 署名姓名，再登记并添加必要署名。复用适用的已有身份，将新 Git 工作副本关联到经核对的作者键，保留已有作者和研究材料，并说明 Git 提交身份的设置情况。 |

## <a id=research></a>研究指令

这些示例用于处理文献和进行数学探索。

### 查找、登记或审计文献

| 指令示例 | Agent 的预期行动 |
| --- | --- |
| 查看本地文献 abc26，入库并审计 | 核对 abc26 的作品、版次和本地原件，补齐书目，按需维护版次及原文位置说明。原文有目录时，整理为可检索的文献目录。审计其数学内容，记录实际检查范围、结论和未解决问题。 |
| 审计文献 abc26 的定理 1.7 | 定位原文定理 1.7，核查完整陈述、假设、证明及必要依赖的适用性，记录审计结论、未检部分和具体缺口。 |
| 搜索 On the construction of S，尝试入库并审计 | 识别作品与版次，检索已有材料并尝试获取原文；补齐书目，按需维护取得版次及来源位置的说明。原文有目录时，整理为可检索的文献目录。审计取得的内容，报告获取失败、不可用部分和实际检查范围。 |
| 这个定义在相关文献如何使用的？ | 查阅已有定义记录和相关原文，比较对象、假设、符号及使用场景，给出准确引用，并区分来源定义与本地改写或推广。 |

### <a id="start-or-continue-research"></a>[研究任务](../用户手册.md#material-task)

| 指令示例 | Agent 的预期行动 |
| --- | --- |
| 把 abc26 中的猜想 1.3 设为 [W 系](../用户手册.md#notion-research-line-letter)任务 | 核对猜想 1.3 的原文、假设和范围，先查找已有同题 Task；需要新建时使用 W 系，写明来源、精确问题和完成标准。 |
| 以如果 P，则 Q 设置一个任务，F 系 | 明确 P、Q 的对象、假设和量词，以“P 蕴含 Q”为完整目标建立 F 系 Task，并明确完成标准。 |
| 将命题 P 从有限维情形推广到无限维情形，建立新任务 | 核对原命题，明确新对象、假设和拟证明的结论，建立 Task，并将原命题保留为应涵盖的特例。 |
| 设置任务：找到在 P 情形下的一般公式，能覆盖 abc26 中公式 (1) | 核对原公式的假设和记号，明确 P 情形及一般公式的适用范围；建立 Task，把公式的正确推导及其如何涵盖原公式写入完成标准。 |
| 开始推进任务 F0001，直到周用量剩余 5% | 核对任务现状和有效执行条件，确认能读取适用账户的周用量；无法读取时说明限制并暂缓推进。满足执行条件后推进研究，监测剩余额度，在首次观测到剩余不高于 5% 或监测失效时停止，保留有用结果、未决问题和续研位置，并记录有效停止条件。 |
| 整理当前进展后暂停 | 完成当前轮次的核查与整理，保留有用结果、失败尝试、剩余问题和可继续的位置，记录暂停及仍有效的条件，然后停止继续推进。 |
| 汇报 F0001 的当前进展 | 核对任务现状，区分已证明结果、候选论证、计算观察和未决问题，给出相关材料链接，并说明距离原始目标还缺什么。 |
| 继续推进任务 F0001 | 读取当前目标、策略、已有成果和停止条件，在本次授权及仍有效的限制内恢复推进；遇到尚未解除的停止条件时，说明阻碍继续的具体原因。 |

## 管理指令

这些示例用于 [Git](../git-repository.md#notion-git) 操作、环境设置和日常维护。

### [提交](../用户手册.md#notion-commit)与[推送](../用户手册.md#notion-push)

| 指令示例 | Agent 的预期行动 |
| --- | --- |
| 提交，推送 | 确定本次交付范围，保留其他暂存工作，核对真实身份、分支和目标远端；确认连接后创建提交并推送，报告提交范围和远端结果。 |
| 提交、推送 F0001 对应的手稿目录下改动 | 定位 F0001 对应的手稿项目，仅提交指定目录内应纳入 Git 的改动，保留其他工作；确认身份、目标和连接后推送，并报告实际范围。 |
| 提交工作区全部改动 | 确认工作区全部改动及作者归属，将应纳入 Git 的内容创建为本地提交，保留忽略规则排除的文件，并报告提交范围和剩余改动。 |
| 提交推送，不做任何检查 | 不运行内容审查、格式检查、测试或额外扫描；仅进行完成 Git 交付所必需的范围、身份、目标与连接确认，完成指定提交和推送并报告结果。 |

| 指令示例 | Agent 的预期行动 |

### 日常维护

| 指令示例 | Agent 的预期行动 |
| --- | --- |
| 启用/关闭本仓库的框架版本自动检查 | 根据你选择的启用或关闭要求更新本仓库设置，保留其他配置并报告当前开关状态；启用后按每个 UTC 日的自动检查规则工作。升级仍须实际明确授权。 |
| 升级框架到最新版本 | 核对已安装版本与官方最新版本，有更新时固定目标版本和提交，依据升级说明完成受影响文件适配及必要检查，保留本地改动、研究材料、个人设置和有效执行条件。通过检查后更新安装版本；实际多人共享 Git 仓库按默认授权提交、推送并确认远端结果，遵守本地处理、离线或禁推等明确限制。报告升级前后版本、目标提交、检查和交付结果，以及无更新或未完成事项。 |
| 按框架规则处理合并冲突 | 核对双方改动、作者归属和实际权限，直接处理可确定的管理类冲突，包括保持对象和数学含义不变的定位修复。实质数学分歧保留双方证据，说明差异并依据已有授权或取得必要授权后进行限定复核；对他人内容的实质修正保存在修正者自己的材料中。检查合并结果和受影响引用，报告处理结果及未决事项。 |
| 分析 `.tmp` 下的文件，确认可以删除后删除 | 核实文件用途和使用状态，先保留尚未存入正式材料的必要内容，再删除已确认可弃且未被其他活跃会话使用的临时文件。 |
| 按框架规则核查本地数学材料是否符合规范 | 按本次范围，由与修复、验收阶段隔离的 agent 分批只读核查本地数学材料及必要输入和引用，检查作者、版本、评估、来源、审查绑定等是否符合现行规则。规范问题记入 `maintenance`，实质数学问题记入 `erratum`，报告实际覆盖、未检范围和未决事项。 |
| 查看maintenance和erratum，按框架规则进行修复 | 读取本次范围内的待修项，由符合阶段隔离要求的 agent 核实问题，在实际作者权限内修复、自检并检查必要消费者。规范修复交由独立 agent 验收，数学错误按实际版本、评估和数学审查要求处理；保留原问题、依据、验收要求及未修、未验收事项，报告修复范围和剩余限制。 |
| 按框架规则验收材料修复 | 由未参与同范围核查或修复、未继承相关实质讨论的独立 agent，对照原问题和现行规则检查待验收修复及必要消费者，报告通过或不通过的范围。按作者或接收方的实际处置权限清理已验收部分，保留失败、未验收、越界及并发新增事项；验收阶段不修复材料，规范验收不等于独立数学审查。 |
