## ACME：自主与协作数学探索

ACME 是一个用于自主与协作数学研究的轻量框架。
它将面向 AI agent 的 Markdown 规则与辅助脚本结合，用于支持持续探索，并保留可供检查、复用和继续推进的研究成果。
它有两个主要用途：让自主 AI agent 在人类数学家的指导下开展数学研究，以及支持人类作者之间的协作。

### 人类数学家

人类数学家负责：

1. 确定研究问题、授权范围和完成标准，以启动 [Task](#material-task)。
2. 与 agents 一起指导[研究策略（Strategy）](#material-strategy)的发展。
3. 贡献想法、澄清数学意图、确定研究优先级、质疑论证、完善问题，并调整研究方向。
4. 理解研究产出，探索数学知识的前沿。
5. 对数学结果负责。

### 由[大语言模型（LLM）](#notion-llm)驱动的 agent

在授权范围内，自主 agents 负责：

1. 研读文献，核查研究所需的结果。
2. 发展和评估[研究策略（Strategy）](#material-strategy)，识别缺口，并在所分配的工作内自主作出常规方法决策。
3. 探索开放性问题，澄清新结果的适用范围和局限。
4. 为具体问题寻找证明和反例，运行可复现计算，以获得观察、证据和启发。
5. 在适当的研究材料（包括 [Claim](#material-claim) 和 [Ledger](#material-ledger)）中保留假设、论证、证据、依赖关系、有价值的失败方法、未解决问题和实质研究历史。
6. 按要求安排独立[审查（Review）](#material-review)，并记录其范围、发现和局限。
7. 按照一般数学写作标准和负责作者的偏好准备、审查手稿。

### 协作

数学家可以通过共享的 [Git 仓库](git-repository.md#notion-git-repository)开展协作，共享研究材料，并复用彼此的成果。
仓库可以托管在 [GitHub](git-repository.md#notion-github) 等平台，供协作者在各自的设备上开展工作并同步改动。
参见 [Git 仓库协作示意图](git-repo.png)。

同一仓库中的协作者可以为共同数学目标建立联合 [Task](#material-task)，明确共同问题、假设和完成标准；各人通过自己的 Task 确定参与范围，并以[研究策略（Strategy）](#material-strategy)组织研究路线。
建议比较协作者已有的路线、可复用结果和有启发的失败，并在有用时选择不同策略，减少重复的数学工作。
为了独立验证、复现和交叉核查，也可以有意沿用同一路线。
请在自己 Task 的参与范围和现有执行条件内选择方法；这些建议将数学判断留给协作者。

不同数学家或团队也可以通过[接收（Intake）](#notion-intake)选定材料开展跨仓库协作，参见[跨仓库协作示意图](collaboration.jpg)。

### 工作流程

研究从人类确定的 [Task](#material-task) 开始，并明确其完成标准。
Agents 首先查阅和复用相关本地研究材料及文献，再按需上网查找补充来源。
它们核查结果的适用性，发展[研究策略（Strategy）](#material-strategy)，反复尝试证明、计算和寻找反例。
每次尝试都为下一次提供依据：有用的发现、失败和未解决问题会保存在适当的研究材料中，包括 [Claim](#material-claim) 和 [Ledger](#material-ledger)。
研究策略会在授权目标内调整。
候选结果接受数学[审查（Review）](#material-review)，Task 是否完成则依据原始标准判断。

参见[工作流程图](workflow.jpg)。

## <a id="setup"></a>设置

新研究项目请依次完成以下步骤 I–III。
若加入已有合作，请先设置工作区，再按加入合作的步骤操作。

### 步骤 I：选择能力合适的[大语言模型](#notion-llm)

比较大语言模型处理研究级数学问题的表现。
可参考 [FrontierMath Tier 4](https://epoch.ai/frontiermath/tiers-1-4?tier=Tier+4+%28v2%29&view=graph&tab=leaderboard)、[MathArena](https://matharena.ai/models)、[Riemann-bench](https://surgehq.ai/benchmarks/riemann-bench) 等相关评测。
选择用于数学研究和管理事务的模型时，考虑其开源情况、可获得性及成本。

### 步骤 II：设置工作区

在单台设备上进行个人研究时，选择合适的 [agent 运行环境](agent-harness.md)，并接入能力合适的[大语言模型](#notion-llm)。

1. 安装 agent 运行环境，可以选择独立应用，也可以选择在[集成开发环境（IDE）](agent-harness.md#notion-ide)中使用；按需或按个人意愿登录。
2. 在设备上选择一个文件夹，用于存放框架及后续研究材料。
3. 在设置或模型选择器中选择模型及服务提供方。

若要跨设备同步工作、与其他数学家协作，或方便他人获取你的研究产出，可结合使用 [Git 仓库](git-repository.md#notion-git-repository)和 [GitHub](git-repository.md#notion-github) 等云平台。
框架支持基于 [Git](git-repository.md#notion-git) 的同步和协作。

4. 在设备上安装 Git，或请所选运行环境中的 agent 代为安装。
5. （可选）如有需要，创建或登录仓库托管账号，然后连接已有仓库或创建新仓库。

- 参见[设置指令示例](user-instructions/用户指令.md#setup)。

### 步骤 III：安装并初始化框架

若要加入的已有研究仓库已经包含 ACME，请改按下一节的步骤操作。

1. 请 agent 将 [ACME 框架](https://github.com/vtejdn/acme)下载到项目文件夹；若使用 [Git](git-repository.md#notion-git)，也可以[克隆](#notion-clone)其仓库。
2. 选择唯一的作者键，例如 Alice 或 Ali，请 agent 将你登记为作者。
   在 Git 工作区中，请 agent 将这个工作副本关联到你的作者键，以便新记录使用正确的作者归属。
3. （可选，使用 Git 时）配置[提交](#notion-commit)所使用的姓名和邮箱，或请 agent 代为配置。
4. （可选，使用 [Git 仓库](git-repository.md#notion-git-repository)时）为研究仓库选择一个简短、易辨识的名称，并请 agent 配置仓库身份。
5. （可选）在适当的时候，我们强烈建议通过公开仓库分享研究记录。

### 以协作者身份加入已有 [Git 仓库](git-repository.md#notion-git-repository)

1. 登录仓库托管平台，接受合作者的邀请。
2. 请 agent 协助配置共享仓库的访问权限。
3. 将仓库地址提供给 agent，请它把仓库[克隆](#notion-clone)到新的本地文件夹。
   在 agent 运行环境中打开该文件夹。
4. 如果你尚未在研究仓库中登记，请选择一个与协作者不同的作者键，并请 agent 登记。
   请 agent 在 ACME 中将这个工作副本关联到你的作者键。
5. 配置 [Git](git-repository.md#notion-git) [提交](#notion-commit)所使用的姓名和邮箱，或请 agent 代为配置。

## 开始使用

### 开始一个 Task

1. （可选）提供相关文献，或请 agent 查找。
   请 agent 将来源文件保存在[本地文献目录](../mathematics/literature/pdf)，并按要求的深度审查相关文章的指定部分。
2. 通过与 agents 讨论建立 [Task](#material-task)，明确问题、约束和完成标准。
   你可以选择一个[研究线字母](#notion-research-line-letter)，用于组织该 Task 及其相关材料。
   示例见[常用指令](#常用指令)。
3. 对于持续的自主研究，明确或采纳执行限制及停止条件。
   参见[研究指令示例](user-instructions/用户指令.md#start-or-continue-research)。
4. 在提示时批准必要的工具操作，并回应 agents 提出的问题。
5. 思考并理解 agents 提供的数学材料（任何 agent 都无法代替你完成这一步）。
   与 agents 讨论数学，以加深并加快理解。
   索取相关参考文献，并以苏格拉底式的追问方式询问论证和想法的来源，尤其是那些依赖模型知识、却没有明确来源依据的论证。
6. （可选，使用 [Git](git-repository.md#notion-git) 时）[提交](#notion-commit)想要保留的改动；需要时撤销本地编辑或还原已有提交。
   与其他数学家协作时，请 agents 处理[拉取](#notion-pull)、[合并](#notion-merge)，并协助解决冲突。

### 注意事项

- Agents 会尝试将公开可获取的文献下载到[本地文献目录](../mathematics/literature/pdf)。
  默认情况下，[Git](git-repository.md#notion-git) 会忽略此目录。
  如果把自己的私密材料放在这里，请确保 Git 忽略此目录，并且不将其上传到公开仓库。
- 如果协作者原本会使用相同的作者键，请约定不同的键，例如 Wang1 和 Wang2。
- 对于由不同主研究 agent 并行推进的 [Task](#material-task)，使用不同的[研究线字母](#notion-research-line-letter)。
  在设置 Task 时选定字母，以分开材料编号并减少写入冲突。
  请 agents 协调共享文件的改动，包括索引、书目和仓库身份记录。
  不建议另建并行研究 worktree；框架没有为其规定管理流程。
- ACME 通过书面规则和辅助工具指导 agents。
  如果 agent 偏离你的指令或框架规则，请它解释差异并纠正受影响的工作。
- 框架规则可能存在歧义、不一致或缺漏。
  如果你认为有必要，可以请 agent 修改框架规则。
  也欢迎向 ACME 框架的[作者](https://github.com/vtejdn)反馈。

### 有用的习惯

- 对框架有疑问时，随时询问 agent。
- 如果文献保存在由云服务同步的本地目录中，请 agent 通过目录联接（directory junction）将[本地文献目录](../mathematics/literature/pdf)连接到它。
  授予 agent 读取和管理该目录中文件所需的权限。
- 当 agents 自动处理涉及凭据的相关工作时，应妥善保存敏感信息，并将其排除在 [Git](git-repository.md#notion-git) 之外。

## 实用信息

### 框架版本

当前框架版本为 0.1.0。

开始工作时，agent 每个 UTC 日至多自动检查一次[官方 ACME 框架](https://github.com/vtejdn/acme)是否有新版本。
发现新版时，它会说明已安装版本和可用版本，并询问是否安排升级；你作决定期间，当前工作可以继续。
提醒不会安装或升级任何内容，你可以暂缓处理。
你可以要求关闭或启用本仓库的自动检查、立即重新检查，或明确要求升级。
无法确认公开版本时，agent 会说明这一限制，并继续已授权的工作。

### 基本概念

| 术语 | 含义 |
| --- | --- |
| <a id="notion-llm"></a>LLM（大语言模型） | 在大量文本上训练的 AI 模型，能够处理和生成语言，包括数学解释和计算机代码。 |
| <a id="notion-context-length"></a>上下文长度（Context length） | LLM 一次能够处理的输入与输出的最大总长度，通常以 token（文本的小单位）计量。这包括指令、对话历史、提供的材料和生成的回复。 |
| 材料标识 | 用于指明某份材料及其版本（适用时）的结构化标识。例如，`Alice_C_F0007_v1.md` 按作者、类别、研究线、序号和版本标识一个 [Claim](#material-claim)。 |
| <a id="notion-research-line-letter"></a>研究线字母 | 用于组织带编号研究材料的字母，例如 `Alice_C_F0007_v1.md` 中的 F。由 Task 派生的材料继承 Task 的字母，但各自另行编号。未指定研究线时，默认使用 A。 |
| 作者键 | 已登记的人类作者所使用的稳定键，例如 Alice，用于材料标识和作者记录。 |
| 材料家族 | 同一材料保留的各个版本，例如 `Alice_C_F0007_v1.md` 和 `Alice_C_F0007_v2.md`。 |
| 材料版本 | 某份材料保留的一个具体修订版，例如 Claim 的 `v1` 或 `v2` 版本。 |
| <a id="notion-main-research-agent"></a>主研究 agent | 主导某个 [Task](#material-task) 研究工作的 agent，协调参与其中的其他子 agent，并保持研究记录一致。 |
| Task 轮次 | 围绕一个 Task 开展的一段工作；结束时记录进展、未解决问题和可继续的位置。 |
| <a id="notion-git-branch"></a>Git 分支（Branch） | [Git 仓库](git-repository.md#notion-git-repository)中一条有名称的开发线，使改动可以独立于其他工作线推进。 |
| <a id="notion-clone"></a>克隆（Clone） | 将已有 Git 仓库复制到新的本地文件夹，包括其中的文件和版本历史。 |
| <a id="notion-commit"></a>提交（Commit） | 保存在本地 [Git](git-repository.md#notion-git) 历史中的一个版本，记录选定改动及描述这些改动的说明。 |
| <a id="notion-push"></a>推送（Push） | 将本地提交发送到远程 Git 仓库，使这些已记录的工作在远端可用。 |
| <a id="notion-pull"></a>拉取（Pull） | 从远程 Git 仓库获取改动，并将其整合到本地工作中。 |
| <a id="notion-merge"></a>合并（Merge） | 将另一[分支](#notion-git-branch)的改动合并到当前 Git 分支，必要时解决相互冲突的编辑。 |
| <a id="notion-intake"></a>接收（Intake） | 将另一个 ACME 仓库中选定的研究材料引入自己的仓库，同时保留作者归属、来源和审查局限。 |
| 引用键 | 用于标识书目中某项作品的简短标识，使研究记录和手稿能够一致地引用该作品。 |

### <a id="material-task"></a>研究任务（Task）

Task 围绕精确的数学目标组织研究，明确授权范围和约定的完成标准。

| Task 状态 | 对读者的含义 |
| --- | --- |
| `proposed` | 已提出一个研究问题，但尚未将其作为当前开展研究的目标。 |
| `active` | 研究已获授权，并且仍在持续。 |
| `paused` | 研究有意暂停，并有继续的意愿和明确的恢复依据。 |
| `blocked` | 某项缺失输入或未满足前提阻止下一必要步骤。记录会说明恢复进展所需条件。 |
| `completed` | 约定的完成标准已经满足，并有相应数学证据和所需审查支持。 |
| `retired` | 研究已终止。原因、有用发现和尚未完成的部分仍有记录。 |

- 即使当前没有 agent 在工作，Task 仍可能处于 active 状态。
- Task 汇集支持该项研究的材料。
  相关手稿、进展报告及你要求的其他文档，可以集中在 `mathematics/manuscripts/Alice_T_A0007/` 这样的项目中。
- 你可以要求重新激活已完成的 Task，以便继续研究相关目标。
  请说明下一步想研究什么，以及范围或限制有哪些变化。
  实质不同的研究目标应建立为新的 Task。

### <a id="material-strategy"></a>研究策略（Strategy）

Strategy 描述通向研究目标的一条具体路线，包括其机制、剩余障碍和下一步有用工作。

| Strategy 状态 | 对读者的含义 |
| --- | --- |
| `proposed` | 已识别一种可能的方法，但尚未选定为当前研究路线。 |
| `active` | 当前已选定这条路线，用于推进 Task 的目标。 |
| `paused` | 由于优先级、先后次序或可用资源而暂时搁置这条路线，并不意味着数学上的失败。 |
| `blocked` | 某个具体前提尚未满足，阻止下一计划步骤。记录会说明障碍和恢复路线所需条件。 |
| `completed` | 路线已产出其声明的结果或贡献，并有必要证据支持。完成 Task 可能还需要其他工作。 |
| `refuted` | 在所述假设下，经过核查的数学证据排除了已记录的机制，或否定了该机制所需的辅助断言。 |
| `superseded` | 路线已被明确指明的后继 Strategy 替代，或并入另一条路线。其历史和有用发现仍可查阅。 |

- 一个 [Task](#material-task) 可以有多个 Strategy，既可以作为备选路线，也可以作为组合方法的不同部分。
  完成、暂停或排除某一 Strategy，本身并不决定整个 Task 的状态。
- 你可以建议方法、请 agent 比较备选方案，或指定优先级。
  如果优先级或顺序必须保持固定，请明确说明；否则，agent 可以在约定范围内调整路线选择。
- 在授权范围内，自主 agents 可以根据发现和资源变化，新增、修订、重新排序、拆分、合并、暂停或重启 Strategy。
- 失败的路线仍可能提供有用信息。
  它可能揭示障碍、排除一种方法，或指出哪里需要补充假设。

### <a id="material-claim"></a>数学命题（Claim）

Claim 记录一项重要、精确的数学陈述，以及目前对其有效性的认识。

| 数学状态 | 对读者的含义 |
| --- | --- |
| `open` | 精确陈述尚未解决。可以已有部分结果、归约或候选论证，但尚未满足已证明或已反驳的条件。 |
| `proved` | 完整证明在所述假设下确立了精确陈述。所有必要的支持结果均已确立且适用，已有记录的数学[审查](#material-review)未发现尚存缺口。 |
| `refuted` | 经过检查的反例或论证在所述范围内否定了精确陈述。所有必要的支持结果均已确立且适用，已有记录的数学审查未发现尚存缺口。 |

### <a id="material-review"></a>审查记录（Review）

Review 记录 agent 对数学陈述或论证的检查，包括确切输入和范围、发现及未解决的局限。

| 审查关系 | 对读者的含义 |
| --- | --- |
| `self-reviewed` | 证明由参与其形成、或了解其形成过程中数学讨论的 agent 检查过。 |
| `independently reviewed` | 另一 agent 检查了证明，且未参与证明的形成，也未继承相关讨论作为自己的上下文。 |
| `unknown` | 某次旧有审查或来源审查的真实关系尚无法确定；这不意味着存在错误，也不意味着已经进行独立检查。 |

- 这些标签描述审查 agent 与证明的关系，并不表示证明是否正确。
  缺少关系声明与 `unknown` 不同；未选择审查只表示该 Claim 没有选用审查证据。
- 另一 agent 如果继承了证明形成过程中的讨论、数学摘要、作者解释或先前审查结论，其检查仍属于自审。
  仅更换会话或模型，并不能确立独立性。
- [主研究 agent](#notion-main-research-agent) 会在关键证明点安排独立审查，并在 [Task](#material-task) 完成后安排对完整逻辑链的独立审查。
  你也可以要求审查某个具体结果或证明步骤。

### <a id="material-ledger"></a>探索记录（Ledger）

Ledger 保留有用的数学探索，包括比较、失败方法和改变方向的原因。
一条记录可以说明研究了什么、采用哪些假设、尝试过什么、推理或证据表明了什么，以及还有哪些问题未解决。

即使研究尚未形成单独的 [Claim](#material-claim)，Ledger 也可以保留部分论证和有用见解。
例如，失败或未得出结论的尝试可以揭示障碍、区分方法，或帮助避免重复工作。

- 你可以请 agent 比较 [Strategy](#material-strategy)、解释失败尝试、综合多个来源的发现，或为后续工作保留有用的推理思路。
- 你也可以请 agent 记录任何你认为有实质数学意义且值得保留的内容。
